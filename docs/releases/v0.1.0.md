intagent keeps a live, team-wide board of which coding agent, of which team member, is changing which file, so that each agent hears about a teammate's work before it writes the same file. This is the first release.

## Download

- **Archives** for Linux, macOS and Windows, on amd64 and arm64, are attached below. Take the one for your system and check it against `SHA256SUMS` (`sha256sum -c SHA256SUMS --ignore-missing`). Each holds the `intagent` binary (`intagent.exe` on Windows), `README.md`, `LICENSE`, `NOTICE` and `docs/`. The macOS binaries are not signed: if a browser downloaded the archive, run `xattr -d com.apple.quarantine intagent` once.
- **Container image** for the server, for `linux/amd64` and `linux/arm64`: `ghcr.io/patakil/intagent:v0.1.0`, also tagged `latest`. Everything the server keeps lives in its `/data` volume.
- **From source**, with Go 1.26 or later: `go install github.com/patakil/intagent/cmd/intagent@v0.1.0`. An older Go fetches the newest Go 1.26 release to build it by itself, unless `GOTOOLCHAIN=local` is set, as some Linux distributions' Go packages set it: then put `GOTOOLCHAIN=auto` in front of the command. intagent needs 1.26, the oldest Go that still gets security fixes, because a binary takes its runtime defaults from the Go that go.mod names, not from the Go that builds it: while go.mod named Go 1.24, even a binary built with Go 1.27 ignored a container's CPU limit when it sized `GOMAXPROCS`, and accepted SHA-1 signatures in TLS 1.2 handshakes.

The archives and the image are built with Go 1.27; `go version -m intagent` names the exact release.

The same binary is the server, the hook and the CLI. To see it work before you set anything up, run `intagent demo` and open `http://127.0.0.1:7400/`: four simulated agents collide, get refused, send notes and stall.

## What it does

intagent is for teams where several people each run several coding agents in one repository. Each vendor's multi-agent features stop at one person's account, so without it agents of different people meet only at the pull request, when the duplicate work is done and the conflict is there. intagent is one Go binary with no third-party dependencies:

- `intagent serve` is the team server. It holds the board in memory, saves it to disk and serves a live dashboard.
- `intagent hook` is what agents call on their lifecycle events. At session start it tells the agent who else is working in the repository and on what. Before every file write it checks the path against teammates' work. After every write it records the file, and a teammate's agent that touched the same file hears about it at its next step. Between turns it reconciles the changed files with `git diff` against the default branch, so merged or reverted work drops off the board by itself.
- `intagent mcp` is a stdio MCP server with the tools `declare_intent` (shared or exclusive), `check_paths`, `team_board`, `send_note` and `release_intent`.

A working agent that is silent for 10 minutes (45 inside a tool call) shows as stalled, and its exclusive intents stop blocking. After 2 hours it counts as gone. A webhook can tell people about stalled agents and refused edits; Slack incoming webhooks work as they are.

Teammates see your agents' sessions, the files your worktree changed against the default branch, the intents your agents declare, and the first line of each session's first prompt (`intagent login --share-prompts off` keeps your prompts off the board). Only repositories that committed `.intagent.json` are reported. Text one member's agent sends (a task, a note) reaches another's quoted, on one line, capped in length, and marked as information, not instructions.

## Supported agents

`intagent init` sets up every supported agent in a repository, and the team commits the files it writes. For a teammate who has not installed intagent, the hooks do nothing.

| Agent | What `init` writes | Before a write |
|---|---|---|
| Claude Code | hooks in `.claude/settings.json`, MCP server in `.mcp.json` | deny, ask, bump or warn |
| Codex | `.codex/hooks.json` and `.codex/config.toml`; each Codex user also runs `intagent init --trust-codex` | deny, bump or warn on `apply_patch`, also piped through the shell |
| Cursor | `.cursor/hooks.json` and `.cursor/mcp.json` | deny, bump or warn on `Write` and `Delete` |
| GitHub Copilot CLI | nothing of its own: it runs Claude Code's hooks and `.mcp.json` | deny, ask, bump or warn on `create` and `edit` |
| Gemini CLI | hooks and the MCP server in `.gemini/settings.json` | deny, bump or warn on `write_file` and `replace` |
| Any other agent | `intagent guard` as a pre-commit hook (`init --git-hook`), `intagent watch` and `intagent mcp` | the guard refuses a commit into an active teammate's exclusive intent |

Codex, Cursor and Gemini CLI give a hook no way to ask the person, so there an `ask` refuses the edit once and tells the agent to ask its person; the retry goes through.

Hook payloads and answers were checked in live runs against Claude Code 2.1.288, Codex 0.160.0, GitHub Copilot CLI 1.0.91, Gemini CLI 0.62.0 and the agent runtime of `@cursor/sdk` 1.0.35. CI runs the real Codex, Copilot CLI and Gemini CLI, at those versions, against a scripted model on every change.

## When work collides

Each check sorts what it finds by severity, and `team.json` sets the action for each:

| Severity | When | Default |
|---|---|---|
| `block` | an active teammate's claim holds an exclusive intent on the path | `deny` |
| `overlap` | a teammate changed the file, declared a shared intent on it, or holds an exclusive intent with no agent running | `bump` |
| `nearby` | a teammate is working in the same area (package) | `warn` |

`deny` refuses the edit every time, naming the teammate and their task. `ask` lets the person decide; headless agents treat it as a refusal. `bump` refuses the first attempt with an explanation and allows the retry, so the agent cannot miss the warning and is never stuck. `warn` allows the edit and tells the agent once. `off` does nothing.

Changes made through the shell cannot be checked before they happen. If git later shows one inside an active teammate's exclusive intent, every live agent in that worktree is told, and the change is recorded as a breach, which the webhook sends.

To measure how often agents would collide before you enforce anything, start with `{"policy": {"block": "warn", "overlap": "warn", "nearby": "off"}}`. The dashboard counts every check, overlap, refusal and alert per repository.

## Get a team going

On the server, once per team:

```sh
intagent token add alice --config team.json   # prints alice's token once; team.json keeps only its hash
intagent token add bob   --config team.json
intagent serve --config team.json --addr :7400 --data ./intagent-data
```

Or with the image:

```sh
docker run --rm -v intagent:/data ghcr.io/patakil/intagent:v0.1.0 token add alice --config /data/team.json
docker run -d --name intagent -p 7400:7400 -v intagent:/data ghcr.io/patakil/intagent:v0.1.0
```

In each repository, one person runs this once and commits the files it writes:

```sh
intagent init --url https://intagent.example.com
```

Then each member, in each clone:

```sh
intagent login --url https://intagent.example.com   # once per machine; paste your token
intagent init --trust-codex                         # Codex users only
intagent doctor                                     # checks every link and says what to fix
```

The dashboard is at `http://<server>:7400/`; sign in with any member's token. A member added with `token add` can connect to the running server within seconds, without a restart. Beyond a trusted network, serve HTTPS, with `--tls-cert` and `--tls-key` or behind a proxy that terminates TLS, and use an ECDSA P-256 certificate: every hook opens a new connection, and an RSA handshake costs the server about three times as much CPU.

## Scale

v0.1.0 is built for a team of about 200 members running 1,000 agent sessions in 30 repositories, with 100 dashboards open. Two rounds of scale work ran that load against the real server with `scripts/loadgen` and fixed what failed. What the board keeps is bounded however much clients send, and a member who floods the server uses up their own share first.

The last measurement ran commit 91e0b62, built with Go 1.24, on one Linux VM with 4 vCPUs (Intel Xeon, 2.1 GHz): the server on 2 of them (`GOMAXPROCS=2`), loadgen on the other 2, over plain HTTP on loopback. 200 members with 5 agents each sent 200 hooks a second, with 100 dashboards and 300 event streams open. `pre_edit` is the hook that asks before each write. The commits since change crash recovery and how the server stops, and v0.1.0 is built with Go 1.27; the load was not run again on them.

| Board | `pre_edit` p99 | Unchecked edits | Peak memory (RSS) |
|---|---|---|---|
| Seeded with 1,000 idle claims (33,500 changed files) | 57–58 ms | 0 | 136–139 MB |
| Same, plus a burst of 800 more hooks a second for 10 s | 17–32 ms for the burst, 75–93 ms for the rest | 0 | 146–149 MB |
| After 2 simulated hours (177,000 changed files) | 90–93 ms | 0 | 453–507 MB |
| After 7 simulated days (860,000 changed files) | 62–69 ms | 0 | 893–1,026 MB |

- The targets were a p99 under 100 ms sustained and under 250 ms in bursts, no unchecked edits, under 1 GB of memory and under 3 GB written to disk an hour. All were met but memory on the 7-day board, which peaked just over 1 GB in 2 of 3 runs, in the first 10 seconds while 100 dashboards and 300 streams connected; with `--memory-limit 1024MiB` it peaked at 883 MB. By default the server's soft memory limit is 85% of its container's memory limit.
- The p99 figures are from runs on an otherwise idle machine; with 1–2 other cores busy, the sustained p99 was 111 ms.
- The server wrote 0.23 GB an hour to disk over 25 minutes on the seeded board, and sent the dashboards and streams 8.6–10.1 MB/s on average.

## Stops, crashes and restarts

The board lives in memory. With `--data` it is saved in two gzip files: `board.json.durable`, what agents cannot send again (intents and reservations, notes, the activity feed and stats, the sessions keeping reservations live, and which sessions ended), within about a second of a change; and `board.json`, the whole board, at most every 5 minutes while it changes, and at a clean stop.

- **A clean stop** (SIGTERM or Ctrl-C) loses nothing. The server stops taking connections, which hooks take for a restart and try again, answers the requests already under way, and saves the whole board; `serve` exits non-zero if that save fails. A request still arriving a second after the stop began is cut off; if that resets its connection, its hook tries again, and otherwise its edit goes ahead unchecked.
- **A crash** loses about a second of intents, reservations, notes and session ends, up to 30 seconds of the activity feed and stats, and up to 5 minutes of changed files, sessions and what agents were told. Agents at work send their files and sessions again at their next scan or hook; until then a teammate may be bumped once for a file committed since the save, and an agent may be warned again about something it already heard. A session the last whole save had as working comes back unsure, so an agent that died with the server may be reported stalled up to 35 minutes late.
- **While the server is down**, a hook whose connection is refused, or reset before any of the answer came back, as a stopping server resets the connections it had not taken yet, tries again for up to about 3.5 seconds, and then lets the edit through, or refuses it if `INTAGENT_FAIL=closed` is set; the agent is told later which of its edits went ahead unchecked. A retry can only turn an unchecked edit into a checked one: had the server decided the edit before the reset, it answers the same edit again as the board stands, refusing it again if a reservation does, but without a bump or heads-up the first answer spent. In the measurement above, the server answered `/healthz` again 2.2–3.3 seconds after SIGTERM, and 45–75 of about 1,275 edits in the 40 seconds around the restart went ahead unchecked.
- **Downtime does not count as agents' silence**: agents still at work are not reported stalled when the server comes back, and their reservations keep refusing teammates.
- **A damaged `board.json`** is set aside and the previous save, `board.json.prev`, restored in its place; keeping that previous save means the whole board takes twice its size on disk. A damaged durable part is set aside, and what it held since `board.json` is lost. If saves fail, on a full disk say, the server keeps every change in memory, retries, logs the failure and reports it in `/healthz`.

## Known limits

- **Shell changes** are not checked before they happen; intagent finds them in git afterwards.
- **It fails open by default.** A hook waits 2 seconds (`INTAGENT_TIMEOUT`) and then lets the edit through, or refuses it with `INTAGENT_FAIL=closed`. When more than 5% of the last 10 seconds' edits go ahead unchecked, the server reports itself degraded on the dashboard, in `/healthz` and, if configured, by webhook.
- **Large edits are partly checked.** An edit is compared with all of teammates' work on its first 200 paths, and with their reservations on up to 2,000; the agent is told what was not checked. Under load, an edit that names more than about 200 files may be answered unchecked. A worktree reports at most 2,000 changed files.
- **Members without intagent installed are not on the board**: their agents' edits are neither checked nor reported.
- **Subagents.** Each Claude Code subagent hears about a collision itself. Support for Codex and Cursor subagents was written from those agents' source code and has not been run live. Copilot CLI and Gemini CLI do not say which subagent made an edit, so the board cannot tell their subagents apart.
- **Cursor** was tested through the `@cursor/sdk` agent runtime, not the Cursor editor. A Cursor too old for `preToolUse` hooks gets only the MCP tools. On Windows, Cursor runs hooks in PowerShell, which cannot run intagent's hook command, so there Cursor works without intagent.
- **Trust and start directory.** Codex runs only hooks it trusts: each Codex user runs `intagent init --trust-codex`, and again after each upgrade. Claude Code and Gemini CLI run project hooks only in folders you trust, and read them only from the directory they start in; if you start an agent in a subdirectory, run `intagent init --user`. Headless Claude Code runs need `--allowedTools 'mcp__intagent__*'` to use the MCP tools.
- **Windows** binaries are built and CI vets the Windows code, but the tests run only on Linux and macOS.
- **One server per team.** The board is held in memory, with no replication or failover. By default the server keeps up to 20,000 sessions, and past 20,000 claims with no agent running it forgets those quiet for a day: twenty times the target scale. Nothing beyond the target scale was measured.
- **Memory grows with unmerged work.** Changed files are capped at 512 KB per claim and 32 MB per member. In a 24-hour simulation where no branch was ever merged, the heap grew from 145 to 320 MB and was still rising.
- **A reservation in a worktree an agent has left for good** keeps blocking teammates until that session ends or goes quiet.
